# How Momentic works (public research)

Compiled November 2026 from Momentic's public documentation
(`momentic.ai/docs/llms-full.txt`), its published YAML format reference, and
its engineering blog. Momentic's actual prompt text and source are **not
public**; nothing here comes from decompiling their CLI. Memento's
implementation is original and written from these public descriptions.

## 1. The AI "sublayer"

| Aspect | What Momentic does | Source |
| - | - | - |

| Memory | Past locator/assertion decisions (incl. failures) are fed back to the agent to resolve ambiguity consistently ("the selected tab"). 30-day expiry, per org. | Docs: Memory |

## 2. Prompting / authoring techniques they document

These are the rules their agents are evidently built around (they tell users
to write steps this way, and the agents are tuned to it):

**Element descriptions**
- Shortest description that uniquely identifies the element *for a user*.
  Start with purpose / accessible role + name, add stable context (dialog,
  row, heading) only to disambiguate.
- Avoid CSS/XPath, `data-testid=…`, references to earlier steps, and
  over-specified styling.
- **Single-quoted text is a strict requirement**; unquoted text tolerates
  rewording, truncation, typos (`john@@gmail.com` matches `john@gmail.com`).
- Visual and positional cues are allowed but limited to the viewport.
- Interpolated `{{ }}` values are part of the cache identity.

**Assertions**
- Under ~20 words, one focus each, clearly true/false, no actions inside
  ("wait for…"), nothing subjective or imperceptible (hex colours), nothing
  transient (toasts, spinners) — assert the durable side effect instead.
- Evaluated against DOM + accessibility tree + viewport screenshot.
- "Run assertions" check things that were true *at some point* by sampling
  frames from the run video after the run.

**AI actions (`act`)**
- One bounded user intent with a clear stopping point; split long flows into
  semantic phases (each `act` is a checkpoint in the trace).
- `precondition` / `postcondition` are **protected guards the agent cannot
  edit or skip**. The agent **cannot pass its own step**: an independent
  reviewer checks settled page state + recorded actions + goal.
- No unbounded loops; the agent has an execution budget and stops instead
  of repeating ineffective actions.
- Pass data the agent can't infer through variables.

## 3. Agent architecture details (engineering blog)

**AI Action v3** — three phases: *execute* (tool-calling agent reaches the
goal and records a replayable trajectory), *replay* (no LLM call), *heal*
(re-invoke the agent to repair the trajectory). Three tools:
- `execute_step` — CLI-like commands (`--step-type CLICK --description "…"`)
  translated by a subagent into normal steps; results carry a cache id and
  `role`/`name`.
- `splice_generated_steps(steps, startIndex, deleteCount)` — edit the stored
  trajectory in place while healing.
- `finish(success, message, autoGeneratedPostcondition)` — the postcondition
  future replays must satisfy.

Earlier versions: v1 = one LLM call per step returning the next command,
steps cached in YAML (noisy diffs); v2 = two calls per step (critique +
choose), no cache — slower and less deterministic.

**Locator caching / "user intent"**
- Locator outputs a list of unique CSS selectors + a DOM-node snapshot.
- Replay evaluates all selectors, groups by matched element, and picks the
  element with the most matches, then compares to the stored snapshot.
- The locator **classifies which attributes it used** and which *related
  elements* it relied on; they found results were best when this
  classification comes **after** the reasoning and the answer.
- Stored conditions: required attributes (text, colour, arbitrary attrs) and
  related elements with their own required attributes.
- Fixes: false misses from random class names/ids; false hits on list rows
  (nth-child) after reordering.
- Reported numbers: >95% cache hit rate; ~300 ms cached step vs >5 s uncached.

**Cache storage** — ClickHouse, keyed by test id, step id, CLI version, git
branch and commit timestamp; branches seed from the merge base; caches from
newer CLI versions are ignored; 14-day TTL refreshed on use; only passing (and
eligible: CI or non-main branch) runs write cache.

**Maintenance ladder** — locator auto-heal (in run) → transient failure
recovery (≤3 per run, only preset steps, never hides 5xx/CAPTCHA/regressions)
→ classification (app bug / flaky / env, with heal/warn/fail actions) →
triage agent that re-runs candidate fixes in a live browser and delivers a
PR/commit/patch ("AI routing" picks the branch) → quarantine. Circuit
breaker: skip triage when ≥20 failures and ≥50% failed (probably an outage).

## 4. How Memento maps this

| Momentic | Memento (this repo) |
| - | - |
| Hosted models only | **Bring your own**: Anthropic, OpenAI, Google, any OpenAI-compatible endpoint (Ollama, LM Studio, vLLM, OpenRouter, Groq…); per-agent model + fallback chain in `memento.config.yaml` |
| Tool-calling agents | Structured-output agents (JSON schema per turn) so **small local models work** without reliable tool calling |
| Closed, versioned prompts | Prompts are plain functions in `packages/core/src/ai/prompts.ts`, overridable per project |
| ClickHouse cache, per org | Local JSON cache in `.memento/cache/` (can be committed or ignored); pluggable `CacheBackend` |
| Dashboard knowledge base | `.memento/knowledge/*.yaml`, reviewed in git |
| Chromium only | Chromium, Firefox, WebKit (Playwright) |
| Dashboard run viewer | Playwright trace viewer (`memento trace`) + desktop app run panel |
